# Agent instructions — the hq repo

This repository is the source of truth for the project's mission, research, design, decisions, and issue diagnosis. Implementation lives in the code repos (see `00-META/repos.md`).

Before changing anything here, read the playbooks in `00-META/process/` — every workflow (research, graduation, design amendment, issues, build handoff, external sync, builder-skill sync, parallel work) is documented there, and agents operate through them. Thin skills in `.claude/skills/` wrap these playbooks for invocation (`hq-new-research`, `hq-graduate`, `hq-new-issue`, `hq-defer`, `hq-diagnose`, `hq-amend-design`, `hq-handoff`, `hq-sync-docs`, `hq-status`, `hq-work`); each defers to its playbook as authoritative and adds only the mechanical scaffolding. A fresh instance of this template is configured by the `hq-setup` skill, which fills `05-TOOLS/config.sh` and the 00-META content docs.

Ground rules:

- Work in an isolated workspace, never in a shared clone. **The clones are read-only and a write to one is refused.** Open the workspace with `./05-TOOLS/open-workspace.sh <work-id> [repo...]` — one worktree per repo under `.work/<work-id>/` beside the clones, all on branch `<work-id>`, the hq repo always included and only the code repos you name. Run it again to add a repo mid-work. Push every commit, open a **draft MR on the first push** — it is what claims the work — and **mark it ready yourself** the moment the quality gate is green and every declared predecessor has merged, never earlier and never left undone: draft means "not yet mergeable", ready means the human just reads and merges. **Agents never merge.** Cross-repo landing order is declared in the work item's `lands:` frontmatter, never left as prose. [Playbook 07](00-META/process/07-parallel-work.md). Deterministic mechanics — status rendering, issue allocation, claims, an issue's state fields (`05-TOOLS/set-issue.sh`) — are scripts in 05-TOOLS/, not judgment calls; use them instead of re-deriving their steps.

- Markdown only in the numbered content folders — 05-TOOLS/ is the executable tree; no new top-level folders without explicit confirmation.
- Status lives in YAML frontmatter on research overviews (`status`, `became`), design docs (`status`, `code`, `updated`), and issue reports (`kind`, `status`, `priority`, `located-in`, `fixed-by`, `amended-design`, `claimed-by`, `claimed`, `blocked-by`). Each of the three may also carry `feature:`, naming the doc in `06-FEATURES/` it belongs to; a feature doc itself is prose only, carries no frontmatter, and lists no members — where a feature stands is derived (`05-TOOLS/status.sh --roadmap`, `--feature <name>`), and the roadmap is the ordered list in `06-FEATURES/README.md`. A design doc that only **aggregates** — a README, or an overview that is framing and reading order — carries no frontmatter, because it states no contract to be built or claimed. Never create central status files; cross-cutting status overviews (matrices, badges, the outstanding-by-repo view) are generated from frontmatter.
- `03-DECISIONS` records are immutable: supersede with a new record, never edit meaning.
- `99-ARTIFACTS` and any derived external views (a docs site, a skills marketplace) are strictly downstream — never record a decision there.
- Design docs contain prose and diagrams only — no code.

If the project keeps skills or documentation for people building **on** what it produces, those live in their own derived repos, not here; keeping them current is [playbook 06](00-META/process/06-builder-skill-sync.md). Delete that playbook (and playbook 05) if the project has no such derived views.
